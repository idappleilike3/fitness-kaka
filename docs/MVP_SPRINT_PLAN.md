# MVP_SPRINT_PLAN.md — 成長 MVP 開發順序

## 1. 原則

本計畫在既有 Next.js、LINE、Supabase、餐點分析、會員中心與 NewebPay 上增量開發。不得重做 Sprint 1 的會員建立、LINE webhook、建檔、餐點記錄、訂閱或付款流程。

現有可直接復用的主檔：`members`、`member_profiles`、`meal_records`、`daily_nutrition_summary`、`weight_records`、`subscriptions`、`payment_orders`、`line_events`。所有新功能先以可驗證事件和資料表為基礎，再加 AI 與行銷呈現。

## 2. Phase G0 — 規格確認與計量基線

**出貨內容**

- 確認本文件組的方案、診斷安全邊界、任務定義與有效邀請條件
- 定義事件命名與漏斗儀表板需求
- 補齊隱私、分享預覽、推播同意與風控驗收項目

**不出貨**

- 不改現有會員或付款行為
- 不建立商城、公開排行榜或人格測驗

**完成標準**

- 產品、工程與營運能對每個 MVP 指標、權限與拒絕條件達成一致

## 2.1 使用者留存 backlog（依優先順序）

以下能力支援「體驗／記錄／陪伴」，但尚未全面出貨；每項都必須以真實使用者資料為依據，首頁與 LINE 僅能說明為「陸續開放」：

1. **提醒**：完成提醒同意、時段設定、退訂與每日頻率上限，再發送喝水、運動、記餐提醒
2. **連續紀錄（streak）**：以已確認餐點和 Asia/Taipei 日期計算，處理重送與補登規則
3. **健康分數**：基於已確認飲食、喝水、運動、任務完成資料；資料不足時標示未完成而非推估
4. **徽章**：由可驗證的任務和 streak 解鎖，不使用虛構成效或未驗證事件
5. **每週報告**：彙整週飲食、熱量與目標完成率，提供一個可驗證的下一步

## 3. Phase G1 — 30 天挑戰骨架

**目前實作狀態（2026-07-24）**

- 已實作 migration `supabase/migrations/002_30_day_challenge.sql`：`member_challenges`、任務模板、任務進度與等級／連續紀錄
- 已實作 LINE 指令「開始挑戰」、「今日任務」、「打卡狀態」、「挑戰進度」與餐點確認後的冪等任務／XP／streak 更新
- 已在會員中心摘要顯示 Day、今日任務、連續紀錄與透明的健康分數
- 尚未實作提醒、徽章、每週報告與 AI 減脂診斷，對外須維持「陸續開放」

**出貨內容**

- 資料庫 migration：`member_challenges`、`missions`、`mission_progress`、`user_levels`、`badges`、`member_badges`
- 在既有餐點確認成功事件後，安全且冪等地更新任務進度、XP、streak 與徽章
- 會員中心新增「30 天挑戰」頁：今日一件主任務、連續天數、等級與已解鎖徽章
- LINE 增加任務完成回饋與回流訊息，不改既有餐點辨識流程

**依賴**

- 既有 `meal_records` 確認寫入與 Asia/Taipei 日期規則
- 既有 LINE postback／文字路由模式

**完成標準**

- 首筆確認餐點可完成 Day 1 任務
- LINE 重送、重複 postback 或重試不能重複加 XP
- 不會改變免費圖片＋文字合計 5 次與聊天不計額度的既有規則

## 4. Phase G2 — AI 減脂診斷與 7 天養成

**出貨內容**

- 在既有 profile 與飲食／體重資料上生成「為什麼我瘦不下來」診斷
- 初始診斷從 LINE 導入，完整內容在會員中心展示
- 資料不足時引導連續記錄或補充資料
- Day 1–7 低摩擦任務編排、每日最多一則同意後提醒與 Day 7 簡版報告
- 以真實已確認資料產生初版健康分數與資料不足提示
- Pro 權限開始提供完整診斷與提醒，Plus 保留工具定位

**完成標準**

- 診斷輸出包含資料可信度、行為假設、證據／限制與一個可驗證下一步
- 敏感健康情境安全攔截，不產生醫療或保證瘦身結論
- Free、Plus、Pro 的報告可見範圍符合 `CONVERSION_AND_RETENTION.md`

## 5. Phase G3 — 分享與邀請閉環

**出貨內容**

- `share_cards`、`invite_codes`、`referrals`、`rewards` migration 與風控狀態
- 診斷、streak、徽章與 Day 7 報告可建立匿名分享卡
- 會員中心的預覽、分享連結與邀請進度
- 受邀者完成診斷＋首筆確認餐點後才標記有效邀請，延遲發放獎勵

**完成標準**

- 卡片不能外洩精確體重、原始餐照或 LINE 身分
- 一位受邀會員只能被歸因一次
- 自邀、重複事件與可疑邀請不會直接授獎
- 受邀者完成漏斗可由事件看見，而非只統計點擊

## 6. Phase G4 — 付費轉換與階段報告

**出貨內容**

- 既有會員中心方案頁加入「Plus 是工具、Pro 是教練」的明確比較
- 重用現有 NewebPay 訂單與 callback 開通，不重建付款
- Day 7、14、30 報告快照與對應 CTA
- 到期前／挑戰里程碑訊息，但遵守提醒頻率與拒絕規則

**完成標準**

- 付款僅在現有驗簽成功回呼後啟用
- 報告資料可追溯且不足資料不捏造
- Free 用戶從額度上限與 Day 7 兩個自然情境進入方案比較

## 7. Phase G5 — 年費與後續成長實驗

**出貨內容**

- 年費 3,590／7,190 的定價、方案定義、付款可行性與退款規則確認後再上架
- 減脂性格測驗、活動代碼、KOL 歸因與合作夥伴能力
- 針對分享卡、任務與升級頁進行受控實驗

**明確不納入此階段前**

- AI 健康商城
- 全站／公開排行榜
- 真人教練媒合、社群牆、複雜課表或影片姿勢分析

## 8. 建議 MVP 起點

若目標是最快驗證差異化與留存，優先順序為 **G1 → G2 → G3 → G4**。G1 先讓既有餐點紀錄變成挑戰行為，G2 才能用真實資料做診斷，G3 再把成果轉成分享，最後用 G4 做合理付費轉換。

每個 Phase 應獨立 migration、測試、產品驗收與小範圍上線；不可為了追求一次完整功能而把所有資料表、AI、分享與付款變更綁成單一發布。

G1 可在完成 migration 後上線驗收
